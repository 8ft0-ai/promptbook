# Progression Recovery

**Conditional contract:** Load for interrupted foreground work, returned evidence, remediation-readiness or a non-standard continuation edge.

Regression case — CryptoPulse Research Brief V1 (#597): if separate implementation authority is established, the repository is accessible and the checkout state can be verified, `/go` must continue from inspection through the next authorised implementation/test/PR transitions rather than ending after tool discovery. If only issue #597 is available, its tracking-only text does not authorise implementation; the correct outcome is a concrete authority decision, not unauthorised mutation.

Treat repository-local instructions, explicit task authority, accepted plans/decisions, current evidence, and platform safety constraints as authoritative.

Before substantive `/go` or `/step` lifecycle progression, resolve the shared progression Resolved Agent Run Context from current authoritative inputs using [Resolved agent run context](../../prompts/workflows/resolved-agent-run-context.md). Bind the governing objective, current lifecycle/candidate/result identity, current review/evidence state where applicable, any material architecture-closure identity and closure-review requirement/disposition, authority and instruction provenance, effective/prohibited capabilities, owner-decision boundaries, continuation mode, proposed next governed action, required preconditions/evidence, completion conditions, any material resolved execution-locality state, and any material resolved fresh-review-context state when independent review is the next gate. Treat `next_governed_action` as a proposal until the exact action passes the existing `/go` action gateway. `/step` consumes that same gateway rather than defining a second authority model.

Before every consequential progression transition, refresh the decision-critical state capable of invalidating the action, re-resolve as needed, and classify the exact proposal as `ALLOW`, `REQUIRE OWNER / SEPARATE AUTHORITY`, or `FORBID`. Execute only an `ALLOW` action that is actually available. Missing or ambiguous authority never defaults to `ALLOW`; technical capability availability never creates authority. If an `ALLOW` action cannot execute through the initially selected mechanism, resolve another eligible execution locality using the resolved-run-context contract before selecting human-operated `EXTERNAL_REQUIRED`. Do not manufacture a new owner-authority decision merely because a mechanism is unavailable.

Before entering another workflow, resolve the effective continuation mode from the workflow router. Apply all hard governance constraints first; continuation mode is only a preference among actions already permitted by those constraints. It never creates mutation, merge, deploy, credential, production, acceptance, review, validation, security, or scope authority.

Use the router-defined modes as follows:
- `auto` — enter the next safely authorised and executable workflow automatically; when that next gate requires independent review, `auto` may satisfy the hard freshness boundary only by entering an eligible isolated fresh-review context, never by treating the authoring context as fresh;
- `suggest` — do not enter the next workflow; when a broader objective remains active, emit the smallest safely determined `Next:` / `Next chat:` navigation;
- `stop` — end after the explicitly requested deliverable without suppressing any required terminal-state classification; when a broader objective is already active, expose safely determined navigation unless the user explicitly requested no continuation guidance.

When the selected command is `/step`, `ONE_TRANSITION` is a stronger progression-depth bound than a downstream workflow's `auto` continuation preference. Complete the one selected governed transition and any verification intrinsic to establishing its result, then re-resolve once and stop; do not enter a second governed transition in the same invocation.

A specialised workflow's local disposition or record is a workflow record, not a conversational terminal state and not authority for the next consequential transition. After recording it, return control to the router and apply the effective continuation mode unless a higher-precedence hard constraint requires a boundary. Consequential transitions must not be inferred from the prior workflow's success record alone.

Continue autonomously while the next action is:
1. inside the current objective and scope;
2. supported by sufficiently current evidence;
3. safely decidable from existing policy, constraints, acceptance criteria, or minimum-safe-change principles; and
4. executable through a legitimately eligible execution locality after any applicable resolved capability-availability and action-specific projection narrowing, or, when the next gate is independent review, satisfiable through a legitimately eligible isolated fresh-review context under the bounded `/review` profile.

Under `/go`, routine planning, implementation, validation, bounded remediation including its required proportional remediation-readiness sweep, closure-review disposition, candidate-review disposition, branch/PR work, merge where already authorised, post-merge verification, and close-out are not conversational stop points merely because they are the “next gate”. Hard closure-review and authority prerequisites still determine whether candidate projection is an eligible transition. Under `/step`, exactly one of those governed transitions may be performed before the required re-resolution and stop. Refresh material state before consequential actions and reconcile changes rather than blindly executing stale instructions.

When governed work resumes after a foreground interruption or session split, apply [Foreground execution resilience](../../prompts/workflows/foreground-execution-resilience.md). Reconstruct current authority, policy, lifecycle state, exact candidate identity, validation/CI state, and material evidence from durable authoritative repository sources rather than prior-chat memory. If a conforming immutable checkpoint exists, recover that exact candidate, reconstruct the governing operation's outstanding candidate-bound assurance from its canonical run context/lifecycle, and resume that assurance before resolving any later boundary. Foreground recovery does not independently establish review-readiness or fresh-review eligibility; for `/fix`, required validation, remediation-readiness, affected evidence rebinding after mutation, and exact final-candidate freeze must remain current for the same candidate before fresh review can become the next gate. The continuation receives no new mutation or lifecycle authority from the interruption, validation evidence remains bound to the bytes it actually covered, the continuation context does not become fresh for review merely because it is new, and foreground-budget pressure does not widen the permitted execution surface.

After a consequential `/go` or `/step` action, bind the resulting lifecycle state, immutable identity, validation and evidence to the state actually observed. Candidate-bound evidence does not silently become result-bound evidence: an approved candidate and its checks remain evidence about that candidate, while a merge commit or other resulting identity requires its own applicable post-action evidence. Re-resolve authority and remaining boundaries before another consequential transition. Re-resolve availability and execution locality as part of that current derived state. When a delegated fresh-review result returns, refresh the exact review-target snapshot identity and current review state before relying on it, plus candidate identity when applicable; for mutable issue/comment targets, locator equality does not preserve freshness when the content/version witness moved. A disposition bound to review-target snapshot A is stale for materially moved snapshot A'. Re-resolve any later remediation, merge, release, deployment, production or close-out authority independently. A successful intermediate action such as merge does not itself imply `COMPLETE`.

When a bounded defect has an objectively determined minimum-safe remediation inside the existing contract, remediate it, run required validation, complete the proportional author-side remediation-readiness sweep, and freeze the exact review-ready candidate without asking for another routine approval. A sweep-discovered sibling correction stays in the same cycle only when it remains inside current remediation authority and passes the `/fix` action gateway; broader authority/design or stronger escalation evidence returns to routing. Do not invent adjacent work merely to keep moving.

Before ending, state why stopping is necessary. If another requested workflow intentionally stops while a broader governed objective remains active and a safe next invocation is durably reconstructible, append the smallest `Next:` or `Next chat:` navigation without executing it in the current context. Prefer the governing objective for `/go` when an intermediate artefact is not the complete lifecycle target, and use `/fix` only when bounded remediation is already authorised. If EXTERNAL_REQUIRED is human-operated external execution, include the explicit executable external action and the evidence to return; a slash command is not a substitute. If EXTERNAL_REQUIRED is the manual fresh-review fallback, emit the minimal durable `/review` handoff only after no eligible/provable isolated review context can satisfy the boundary. If DECISION_REQUIRED applies, use the decision capsule and do not add a command that bypasses it. If BLOCKED applies, do not manufacture `/go`, `/fix`, or `/review` merely to offer motion. If COMPLETE applies, state that no further action is required. If none of EXTERNAL_REQUIRED, DECISION_REQUIRED, BLOCKED, or COMPLETE applies, apply the effective continuation mode: under `auto`, continue the next authorised workflow, including through an eligible isolated fresh-review context where required; under `suggest`, emit the smallest safe navigation without entering the next workflow; under `stop`, end the requested deliverable while preserving any router-required navigation.

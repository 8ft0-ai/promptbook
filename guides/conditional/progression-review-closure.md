# Progression Review Closure

**Conditional contract:** Load for a material fresh-review, strong architecture closure or closure-generation boundary.

When an independent substantive review is the next governed gate, preserve freshness as a distinct information-boundary requirement rather than treating it as execution locality. If the current context is genuinely fresh, enter ordinary [Fresh independent review](../../prompts/workflows/fresh-independent-review.md). If the current context authored, remediated, or materially shaped the review target or candidate and is therefore non-fresh, do not review here. Resolve whether the execution surface can establish an eligible genuinely isolated review context that does not inherit author-side substantive adjudication or expected conclusion. If eligible, invoke the bounded `/review` operation there using only the minimal durable target/reconstruction reference and the ordinary `/review` capability ceiling; require that child context to independently bootstrap applicable authority, reconstruct the exact review target/checks-or-evidence/review state, bind candidate identity when applicable, complete the normal fresh-review contract, and return an exact-review-target-bound disposition/evidence record. Creating or selecting that context is not authority. If isolation is unavailable, ambiguous, or unprovable, preserve the existing manual fresh-context `EXTERNAL_REQUIRED` fallback. Do not route this reasoning-independence decision through the execution-locality ladder.

When current state contains an exact `ARCHITECTURE_CLOSURE_READY` snapshot with `CLOSURE_REVIEW_REQUIRED`, the independent-review target is that **closure snapshot itself** and candidate projection is not yet eligible. Resolve freshness exactly as above and run `REVIEW_TYPE=ARCHITECTURE_CLOSURE`. For a closure snapshot anchored in a GitHub issue/comment, ordinary review write-back records one new bound top-level issue comment; retain its comment ID as a locator but derive `current_closure_review_snapshot_identity` from the locator plus an edit-sensitive review-record witness and the exact closure snapshot reviewed. A read-only/chat-only approval leaves the gate unsatisfied. `CHANGES REQUIRED` rejects that exact closure snapshot but does not imply generic reconstruction. Consume the fresh review's route classification: an eligible `MODELLED_DEFECT` may use the current strong-closure generation's one unused semantic-correction allowance and freeze one corrected snapshot for fresh re-review; an eligible `PACKAGE_ONLY_DEFECT` may use the one unused package-only repair allowance without changing semantic model identity. `NEW_OR_OMITTED_OBLIGATION`, `STRUCTURAL_FALSIFICATION`, `SCOPE_OR_AUTHORITY_MOVEMENT`, ambiguous correction eligibility, or exhausted allowance routes to `GOVERNING_DISPOSITION_REQUIRED`, which terminates active progression for that generation. Do not automatically create a successor closure generation. `APPROVED_FOR_CANDIDATE_PROJECTION` satisfies only the closure-review gate for that exact current snapshot; immediately before projection, revalidate both the closure snapshot and review-record snapshot and re-resolve separate candidate-authoring authority. During projection, if new decision-critical semantics are required outside the approved closure universe, stop projection and route the current strong-closure generation to `GOVERNING_DISPOSITION_REQUIRED`; do not enter reconstruction automatically and do not review the old snapshot again. Closure analysis for a successor is eligible only after a separate governing disposition explicitly authorises a new strong-closure generation. After projection within the approved universe, complete applicable validation/readiness for the exact candidate before fresh candidate review. `/go` must not skip any of these gates merely because author-side closure checks passed.

For strong-closure generations, correction allowances are monotone generation-owned state, not conversational counters. Repackaging, renaming, issue recreation, candidate replacement, snapshot regeneration or another `/go` invocation cannot restore a consumed allowance. If governing disposition later authorises a new strong-closure generation, treat it as a new exact generation identity, preserve terminal predecessor provenance, and do not treat the successor as an automatic continuation of the failed generation. `/go` may continue an already-authorised in-generation correction or package repair, but it must stop at `GOVERNING_DISPOSITION_REQUIRED` for the owner/process decision required there; technical capability does not create that disposition authority.

## Consolidated V2 safeguard

A requirement for another human or formal reviewer is a real hard boundary. An automatically isolated context cannot simulate a mandated different person or formal platform state.

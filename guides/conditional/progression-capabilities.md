# Progression Capabilities

**Conditional contract:** Load when configured capability availability, suppression or PR-ready transitions matter.

When an `ALLOW` action uses a capability with a Promptbook availability key, consume the one `resolved_capability_availability` record derived by the resolved-run-context / [Capability availability overrides](../../prompts/workflows/capability-availability-overrides.md) chain after authority classification and before invocation or projection. Do not independently rediscover Project, repository, work-item, or prior-conversation availability declarations inside autonomous progression. A capability configured as unavailable, or conservatively unresolved because of invalid, contradictory, stale, target-mismatched, or required-but-unavailable configuration, must not be invoked or probed. An `enabled` value removes only Promptbook suppression; it does not create authority, prove executor support, or prove success. Preserve the resolved configuration provenance when it changes execution or fallback behaviour, and verify the resulting state after any attempted capability transition. Locality resolution consumes this same availability state and must not route around an explicitly disabled logical capability by relabelling the same effect through another executor.

For the initial `pull_request.mark_ready` key, avoid creating a transition merely out of habit. If implementation is complete, required validation has passed, any applicable remediation-readiness sweep has completed for the same exact candidate, no genuine lifecycle hold remains, and independent review is the next governed gate, a pull request may be created as non-draft directly. If work, validation, an unresolved decision, repository policy, or another real hold remains, preserve legitimate draft state. When such a draft later becomes reviewable and `pull_request.mark_ready` is configured as unavailable or fails at runtime despite being enabled, do not repeatedly invoke it. Resolve whether another eligible governed connected/native or bounded execution path can perform that same authorised transition without bypassing the configured suppression; only when no eligible governed locality can legitimately perform the transition should the workflow use the bounded `EXTERNAL_REQUIRED` ready-for-review hand-off defined by the availability contract. Never use non-draft creation or locality switching to bypass a real hold.

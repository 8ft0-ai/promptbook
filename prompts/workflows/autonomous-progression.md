# Autonomous progression

## Purpose

Let an engineering agent continue routine, already-authorised work without repeatedly returning to the human for orchestration.

## When to use

Use for a governed engineering objective where repository policy, current evidence, and existing authority determine most routine next actions, but explicit stop boundaries still matter.

## Prompt

```text
Progress <TASK_OR_OBJECTIVE> as far as safely possible with minimal human intervention.

Treat repository-local instructions, explicit task authority, accepted plans/decisions, current evidence, and platform safety constraints as authoritative.

Before substantive `/go` lifecycle progression, resolve the ephemeral `/go` Resolved Agent Run Context from current authoritative inputs using [Resolved agent run context](resolved-agent-run-context.md). Bind the governing objective, current lifecycle/candidate/result identity, current review/evidence state where applicable, authority and instruction provenance, effective/prohibited capabilities, owner-decision boundaries, continuation mode, proposed next governed action, required preconditions/evidence, completion conditions, any material resolved execution-locality state, and any material resolved fresh-review-context state when independent review is the next gate. Treat `next_governed_action` as a proposal until the exact action passes the `/go` action gateway.

Before every consequential `/go` transition, refresh the decision-critical state capable of invalidating the action, re-resolve as needed, and classify the exact proposal as `ALLOW`, `REQUIRE OWNER / SEPARATE AUTHORITY`, or `FORBID`. Execute only an `ALLOW` action that is actually available. Missing or ambiguous authority never defaults to `ALLOW`; technical capability availability never creates authority. If an `ALLOW` action cannot execute through the initially selected mechanism, resolve another eligible execution locality using the resolved-run-context contract before selecting human-operated `EXTERNAL_REQUIRED`. Do not manufacture a new owner-authority decision merely because a mechanism is unavailable.

When an independent substantive review is the next governed gate, preserve freshness as a distinct information-boundary requirement rather than treating it as execution locality. If the current context is genuinely fresh, enter ordinary [Fresh independent review](fresh-independent-review.md). If the current context authored, remediated, or materially shaped the candidate and is therefore non-fresh, do not review here. Resolve whether the execution surface can establish an eligible genuinely isolated review context that does not inherit author-side substantive adjudication or expected conclusion. If eligible, invoke the bounded `/review` operation there using only the minimal durable target/reconstruction reference and the ordinary `/review` capability ceiling; require that child context to independently bootstrap applicable authority, reconstruct the exact candidate/checks/review state, complete the normal fresh-review contract, and return an exact-candidate-bound disposition/evidence record. Creating or selecting that context is not authority. If isolation is unavailable, ambiguous, or unprovable, preserve the existing manual fresh-context `EXTERNAL_REQUIRED` fallback. Do not route this reasoning-independence decision through the execution-locality ladder.

When an `ALLOW` action uses a capability with a Promptbook availability key, consume the one `resolved_capability_availability` record derived by the resolved-run-context / [Capability availability overrides](capability-availability-overrides.md) chain after authority classification and before invocation or projection. Do not independently rediscover Project, repository, work-item, or prior-conversation availability declarations inside autonomous progression. A capability configured as unavailable, or conservatively unresolved because of invalid, contradictory, stale, target-mismatched, or required-but-unavailable configuration, must not be invoked or probed. An `enabled` value removes only Promptbook suppression; it does not create authority, prove executor support, or prove success. Preserve the resolved configuration provenance when it changes execution or fallback behaviour, and verify the resulting state after any attempted capability transition. Locality resolution consumes this same availability state and must not route around an explicitly disabled logical capability by relabelling the same effect through another executor.

For the initial `pull_request.mark_ready` key, avoid creating a transition merely out of habit. If implementation is complete, required validation has passed, no genuine lifecycle hold remains, and independent review is the next governed gate, a pull request may be created as non-draft directly. If work, validation, an unresolved decision, repository policy, or another real hold remains, preserve legitimate draft state. When such a draft later becomes reviewable and `pull_request.mark_ready` is configured as unavailable or fails at runtime despite being enabled, do not repeatedly invoke it. Resolve whether another eligible governed connected/native or bounded execution path can perform that same authorised transition without bypassing the configured suppression; only when no eligible governed locality can legitimately perform the transition should the workflow use the bounded `EXTERNAL_REQUIRED` ready-for-review hand-off defined by the availability contract. Never use non-draft creation or locality switching to bypass a real hold.

Before entering another workflow, resolve the effective continuation mode from the workflow router. Apply all hard governance constraints first; continuation mode is only a preference among actions already permitted by those constraints. It never creates mutation, merge, deploy, credential, production, acceptance, review, validation, security, or scope authority.

Use the router-defined modes as follows:
- `auto` — enter the next safely authorised and executable workflow automatically; when that next gate requires independent review, `auto` may satisfy the hard freshness boundary only by entering an eligible isolated fresh-review context, never by treating the authoring context as fresh;
- `suggest` — do not enter the next workflow; when a broader objective remains active, emit the smallest safely determined `Next:` / `Next chat:` navigation;
- `stop` — end after the explicitly requested deliverable without suppressing any required terminal-state classification; when a broader objective is already active, expose safely determined navigation unless the user explicitly requested no continuation guidance.

A specialised workflow's local disposition or record is a workflow record, not a conversational terminal state and not authority for the next consequential transition. After recording it, return control to the router and apply the effective continuation mode unless a higher-precedence hard constraint requires a boundary. Consequential transitions must not be inferred from the prior workflow's success record alone.

Continue autonomously while the next action is:
1. inside the current objective and scope;
2. supported by sufficiently current evidence;
3. safely decidable from existing policy, constraints, acceptance criteria, or minimum-safe-change principles; and
4. executable through a legitimately eligible execution locality after any applicable resolved capability-availability and action-specific projection narrowing, or, when the next gate is independent review, satisfiable through a legitimately eligible isolated fresh-review context under the bounded `/review` profile.

Routine planning, implementation, validation, bounded remediation, review disposition, branch/PR work, merge where already authorised, post-merge verification, and close-out are not conversational stop points merely because they are the “next gate”. Refresh material state before consequential actions and reconcile changes rather than blindly executing stale instructions.

After a consequential `/go` action, bind the resulting lifecycle state, immutable identity, validation and evidence to the state actually observed. Candidate-bound evidence does not silently become result-bound evidence: an approved candidate and its checks remain evidence about that candidate, while a merge commit or other resulting identity requires its own applicable post-action evidence. Re-resolve authority and remaining boundaries before another consequential transition. Re-resolve availability and execution locality as part of that current derived state. When a delegated fresh-review result returns, refresh the candidate identity and current review state before relying on it; a disposition bound to candidate A is stale for moved candidate A'. Re-resolve any later remediation, merge, release, deployment, production or close-out authority independently. A successful intermediate action such as merge does not itself imply `COMPLETE`.

When an authorised action is not executable through the first mechanism, resolve execution locality proportionately before escalating. Prefer an eligible `connected/native` mechanism, then `hosted/hermetic` execution when the required truth or effect can be established from explicit/remote inputs without owner-private state, then a separately governed `owner-local/bounded-executor` when correctness genuinely depends on owner-local/private state. Each alternate locality must preserve the exact governed action and consume only the existing no-widening action-specific capability projection. This ladder does not resolve review freshness; fresh-review context eligibility is the separate information-boundary mechanism above.

Before generating a substantial owner-operated hand-off, inspect only authoritative repository/task execution or operator surfaces relevant to the action and prefer an established maintained capability with typed invocation-specific identities/expectations. Do not search arbitrary files for executables, build a global tool registry, or invent arbitrary remote shell/argv dispatch. A claim that owner-local execution is required must identify the material private/local dependency; historical convenience or previous owner-shell usage is insufficient.

Handle failed locality attempts distinctly. `PROFILE_DENIED` or equivalent authority/projection denial is not worked around through another executor. `CAPABILITY_DISABLED` is not bypassed by relabelling the same suppressed effect. `EXECUTOR_UNSUPPORTED`, `UNAVAILABLE`, or equivalent execution unavailability may cause re-resolution only among localities already compatible with current authority and constraints. `STALE_PROFILE` or `GUARD_MISMATCH` requires decision-critical refresh before another consequential attempt. Do not retry the same unchanged failed locality indefinitely.

Handle failed fresh-review-context resolution separately. If isolation cannot be established, the child would inherit material author-side adjudication, the durable target cannot reconstruct authority, repository policy requires a distinct human/formal reviewer that the child cannot satisfy, the candidate moves, or the child would need capability beyond the `/review` ceiling, fail closed to the existing manual fresh-context hand-off or the real stronger policy boundary. Retain enough attempt/isolation state to avoid repeatedly creating an equivalent failed review context while the relevant target, isolation and capability state remains unchanged.

Escalate only as one of these states:
- EXTERNAL_REQUIRED — for human-operated execution, the already-authorised required action cannot be performed through any eligible governed execution locality, and one complete executable external action can resolve it; for a genuine fresh-review boundary, automatic isolated-context resolution has first been attempted or determined ineligible and the existing manual `Next chat: /review <durable target>` hand-off is the safe fallback;
- DECISION_REQUIRED — a genuine human judgement/authority decision is needed, such as material scope/outcome/architecture change, permission broadening, security weakening, destructive/production action, material cost, or acceptance of a known failed control;
- BLOCKED — no safe action, eligible execution locality, eligible isolated review context where one is required, complete external handoff, or concrete human decision can resolve the condition now;
- COMPLETE — the governed objective is genuinely finished and required verification/close-out is done.

Fresh independence, missing authority, failed or missing required validation, materially changed accepted proposals, repository/task policy requiring an explicit stop, and the terminal states above are hard boundaries. `auto` must not cross them merely to preserve momentum. An eligible isolated review context satisfies the freshness boundary by providing independent adjudication; it does not remove or weaken that boundary.

When human-operated EXTERNAL_REQUIRED applies, do not merely name the missing capability, credential, receiving context, or external tool. State the one concrete external action the human must perform and provide the smallest complete procedure in the same response. Use a complete copy/paste script or exact commands when command-line execution is appropriate; otherwise give exact browser or UI steps, or another concrete step-by-step procedure. Include material prerequisites, immutable identities, authority/safety guards, fail-closed checks, cleanup/revocation/restore steps, and prohibited actions. State the exact evidence or output the human should return so governed continuation can resume without reconstructing the prior conversation. Do not make the human ask how to perform the external action.

For human-operated command-line execution, apply [Operational artifact hand-off](operational-artifact-handoff.md). Keep a genuinely atomic, transcript-independent command inline. When execution fragility, guard coupling, or evidence complexity is material, prefer a materialised/downloadable artifact with short staging/invocation instructions and bounded `RESULT` / `EVIDENCE` hand-back rather than turning the conversation transcript into executable state. Artifact delivery never creates authority: read-only work remains read-only, and separately authorised mutation must still fail closed on target, identity, prerequisite, integrity, or authority guard failure. If downloadable-file delivery is unavailable, use only a safe degraded path defined by that contract; do not silently substitute a large fragile executable transcript block.

A genuine fresh-context boundary is a distinct kind of EXTERNAL_REQUIRED stop only when the governing workflow cannot establish an eligible genuinely isolated review context automatically. When opening a fresh chat/session is therefore the required fallback and a durable exact target is sufficient for that context to reconstruct the decision-critical state, the smallest complete handoff may be a `Next chat:` public shorthand invocation such as `/review` with that target. The invocation is navigation only, preserves the freshness boundary, and creates no authority. This compact context-transfer form must never replace the complete commands, browser/UI steps, guards, cleanup/prohibitions, or evidence-to-return required for human-operated external execution.

Any script or command sequence presented as the executable handoff must be syntactically complete and self-contained for the stated operation. Do not expose secret values. Do not manufacture an external procedure when the safe action is not sufficiently determined; if no complete executable handoff can be produced, use BLOCKED or DECISION_REQUIRED according to the real unresolved condition instead. A capability limitation with sufficient existing authority is not itself a new decision gate.

If an equivalent external handoff is already durable and decision-critical state has not materially changed, reuse that handoff after refreshing the guards that can become stale, but only after confirming that no newly available or already-established eligible governed locality now removes the need for owner-operated transport. For fresh-review handoffs, also confirm that no newly eligible/provable isolated review context now removes the need for human context transport.

Treat a returned external observation such as PASS or FAIL <material defect> only as evidence for the named check. It does not create new mutation, merge, production, close, or acceptance authority. When the requested evidence is returned unambiguously and existing authority already determines the next action, resume the governing workflow automatically without another routine proceed confirmation. Before a consequential mutation, refresh only the decision-critical state capable of invalidating the returned evidence or next action rather than reconstructing unrelated lifecycle history. Do not delegate an already-established machine-verifiable check to the human merely because execution crossed an external capability boundary. On FAIL, preserve fail-closed behaviour and route the defect through the existing governed scope and authority rather than treating the observation as acceptance.

When DECISION_REQUIRED applies, present the smallest concrete decision as a recommendation-first decision capsule. Put the recommendation and viable choices before supporting governance detail. For multiple meaningful alternatives, use compact labels such as A / B / C. For approval of one bounded proposal, use semantic choices such as ACCEPT / REJECT / CHANGE rather than manufacturing artificial alternatives.

Treat ACCEPT, REJECT, CHOOSE <option>, and CHANGE <instruction> as semantic intents, not required command syntax. Clear natural-language equivalents such as “yes”, “go ahead”, “choose B”, or a spoken option name may express the same intent only when exactly one unresolved decision and its referent are unambiguous. Do not guess when multiple decisions or meanings are plausible.

Bind the capsule to the concrete decision target, proposal/revision identity, recommendation, and bounded effect of acceptance. Before consequential mutation after ACCEPT or CHOOSE, refresh decision-critical state including the exact candidate/result identity, material proposal, applicable policy/checks, governing authority, and repository instructions that could invalidate the accepted action. If the proposal materially changed, do not migrate stale approval; re-present the decision. Consume accepted authority once for that bounded object only, then re-resolve the `/go` context and resume autonomous progression immediately when existing authority permits.

Candidate approval, merge authority, release authority, deployment authority, and production-mutation authority remain distinct. Authority consumed for one consequential action is not ambient permission for the next action; independently gate any later consequence.

REJECT rejects only the presented proposal or choice; it does not implicitly close the objective, undo prior work, or select an alternative. CHANGE requests a revision and is not approval of the revised proposal unless the user's wording explicitly grants authority for that revised proposal.

When a bounded defect has an objectively determined minimum-safe remediation inside the existing contract, remediate and validate it without asking for another routine approval. Do not invent adjacent work merely to keep moving.

Before ending, state why stopping is necessary. If another requested workflow intentionally stops while a broader governed objective remains active and a safe next invocation is durably reconstructible, append the smallest `Next:` or `Next chat:` navigation without executing it in the current context. Prefer the governing objective for `/go` when an intermediate artefact is not the complete lifecycle target, and use `/fix` only when bounded remediation is already authorised. If EXTERNAL_REQUIRED is human-operated external execution, include the explicit executable external action and the evidence to return; a slash command is not a substitute. If EXTERNAL_REQUIRED is the manual fresh-review fallback, emit the minimal durable `/review` handoff only after no eligible/provable isolated review context can satisfy the boundary. If DECISION_REQUIRED applies, use the decision capsule and do not add a command that bypasses it. If BLOCKED applies, do not manufacture `/go`, `/fix`, or `/review` merely to offer motion. If COMPLETE applies, state that no further action is required. If none of EXTERNAL_REQUIRED, DECISION_REQUIRED, BLOCKED, or COMPLETE applies, apply the effective continuation mode: under `auto`, continue the next authorised workflow, including through an eligible isolated fresh-review context where required; under `suggest`, emit the smallest safe navigation without entering the next workflow; under `stop`, end the requested deliverable while preserving any router-required navigation.
```

## Inputs

- `<TASK_OR_OBJECTIVE>` — the bounded engineering objective and any relevant governing issue/plan/reference.

## What it does

Separates genuine human decisions, execution-capability boundaries, and review-information boundaries from ordinary lifecycle status, reducing repeated human orchestration while retaining fail-closed behaviour. It applies the router-owned continuation preference only after hard constraints have been satisfied, so local workflow records do not accidentally become terminal states and `auto` cannot manufacture authority. For `/go`, it resolves explicit authority/capability state before consequential progression, classifies the exact transition through the shared action gateway, refreshes stale-able state before execution, consumes the one Promptbook-resolved capability-availability record as a no-widening execution filter, resolves eligible execution locality before human-operated fallback, and separately resolves an eligible isolated fresh-review context before manual fresh-context fallback. A delegated reviewer receives only the bounded `/review` profile, independently reconstructs authoritative decision-critical state, and returns evidence bound to the exact candidate it inspected. The originating workflow refreshes that state before any later consequence, so neither `APPROVED` nor `CHANGES REQUIRED` creates ambient continuation authority. For draft pull requests, it avoids an unnecessary ready transition when a candidate is genuinely reviewable at creation time while preserving legitimate draft holds and using a bounded external fallback only after no eligible governed path can perform a later required transition. When a capability boundary genuinely requires human-operated external execution, it reduces the human role to performing one explicit, complete action and returning the requested evidence rather than working out how to continue. Material execution-state hand-offs use the operational-artifact contract so complex procedures can be materialised with coupled guards and bounded evidence while genuinely atomic commands remain inline. A genuine context-transfer boundary uses the existing minimal reconstructible next invocation only when automatic isolated review cannot satisfy freshness. Returned external evidence is scoped to the named check and governed work resumes automatically when existing authority already determines what follows. When a human decision is genuinely required, it presents a compact device-neutral decision capsule and resumes governed autonomous progression after an unambiguous bounded response.

## Boundaries / limitations

This prompt never overrides repository-local policy or grants credentials, merge, release, deployment, production, destructive-action, material-cost, or permission to widen scope merely because `/go`, a technical capability, an executor, a locality, an isolated context, or an availability setting is present. Autonomy is limited to actions already justified by the governing objective and current authority/evidence. Capability availability configuration may narrow execution only; it is not action authority and does not prove mechanism health. Autonomous progression consumes Promptbook's resolved availability state; it is not a configuration-discovery authority. Execution-locality selection is likewise derived execution state, not a global capability registry, executor implementation, credential broker, arbitrary remote shell mechanism, or authority source. Fresh-review context resolution is a distinct information-boundary mechanism, not a claim that any new prompt, process, account, model label, tool, or executor is automatically independent. The authoring context never becomes fresh through delegation, and a repository rule requiring another human or formal reviewer is never simulated by an isolated model context. Continuation mode is a preference, never authority. Suggested next invocations are navigation only. An external handoff must not expose secret values, invent an unsafe procedure, or substitute shorthand navigation for a complete human-operated external action merely to avoid a stop. Artifact delivery is a hand-off mechanism, never new execution or mutation authority; unavailable file delivery must not trigger a large fragile transcript fallback. Returned observations and delegated review dispositions are evidence, not new authority. Short natural-language or voice responses are authority only when their decision referent is unambiguous; materially changed proposals must be re-presented rather than inheriting stale acceptance.

# Fresh independent review

## Purpose

Review a candidate, design, or evidence record from a genuinely fresh context without inheriting the previous session's substantive conclusion.

## When to use

Use when independence is part of the quality or governance boundary: substantive PR review, design review, evidence adjudication, close-out review, or another decision where author-side reasoning should not be treated as approval evidence.

## Prompt

```text
Conduct a fresh independent review of <REVIEW_TARGET> against <GOVERNING_CONTRACT>.

Treat prior summaries, recommendations, and conclusions only as navigation aids. Reconstruct the material authoritative state directly from the actual candidate and decision-critical evidence. Establish the current identities, revisions, checks, review state, and governing requirements needed for this decision.

Before substantive adjudication, resolve the ephemeral Resolved Agent Run Context defined by `prompts/workflows/resolved-agent-run-context.md`. Derive it from current authoritative inputs rather than conversation memory. Resolve the operation, repository identity, work-item identity, immutable candidate identity where applicable, authority sources, applicable repository-instruction provenance, effective and prohibited capabilities, owner-decision boundaries, and required evidence. Treat that context as derived execution state, not as a new authority source. If a required field or authority source cannot be resolved safely, fail closed or hand off according to the governing workflow rather than filling the gap from remembered conversation state.

When this review is entered through delegated fresh-review context resolution, first verify that the receiving context is genuinely isolated from the authoring/remediation context's substantive adjudication and expected conclusion. Eligibility requires affirmative evidence that the receiving context does not inherit author-side private reasoning, hidden conversational state, proposed disposition, or a substantive summary that would substitute for independent inspection. A new prompt, model label, agent name, process, account, tool, or executor is not sufficient by itself. Project/repository instructions, governing work items, exact review-target identities, candidate identities when applicable, checks/evidence and other authoritative durable records remain valid because the receiving reviewer must reconstruct and adjudicate them independently.

A delegated fresh reviewer should receive the minimal durable review target or equivalent reconstruction reference needed to locate the governed review. It must independently bootstrap applicable project/repository authority, reconstruct the exact review target, governing contract, checks/evidence and current review state from authoritative sources, bind candidate identity only when the target is a candidate, resolve its own `/review` run context, and complete this ordinary fresh-review contract. For candidate review, this includes reconstruct the exact candidate and its checks from authoritative sources. The originating context's broader operation profile does not transfer. The child review context is constrained by the `/review` operation ceiling and may receive only the current review capabilities required for the review, such as `repository_read`, `work_item_read`, `ci_evidence_read`, and `review_publish` only where ordinary `/review` already permits write-back. It must not inherit candidate mutation, bounded `/fix` mutation, merge, release, deployment, settings, provider, production, credential, or other author-side capability merely because the parent context possessed it.

Preserve the delegation invariant:

```text
child_review_authority ⊆ effective_review_authority
```

Creating or selecting another context is not authority. If establishing the context would require a capability or effect outside the current `/review` ceiling, if isolation cannot be proved, or if the durable target cannot reconstruct the required authority safely, the delegated context is ineligible and the governing workflow must use its fail-closed fallback rather than treating the child as independent.

Determine the review-recording mode from the governing invocation before writing anything. When this workflow is selected by an ordinary router `/review` for a GitHub pull request, write-back is the default and includes only the narrow authority required to record the requested review. When `REVIEW_TYPE=ARCHITECTURE_CLOSURE` targets a closure artefact anchored in a GitHub issue or issue comment, ordinary router `/review` also defaults to write-back, but only as one new top-level comment on the owning issue containing the exact edit-sensitive closure snapshot identity, the single closure-review disposition and concise rationale. The created comment ID is only the durable review locator. The consumable `architecture_closure_review_identity` must additionally bind an edit-sensitive snapshot of that review record (for example canonical body digest plus repository-native version/update witness) and the exact closure snapshot it reviewed. Closure-review records are append-only evidence for this gate: if a record is edited in place, its prior fresh-review identity is invalid and later projection must not consume it. If the target has no permitted durable repository-native review-record location, report the assessment but mark the closure-review gate unsatisfied rather than inventing a durable identity. When the caller explicitly selected `/review --read-only`, `review without mutation`, `review only in chat`, or another unambiguous zero-write qualifier, perform the assessment with no GitHub write-back; a read-only closure-review result is assessment evidence only and cannot satisfy a gate that requires a durable closure-review identity. When this prompt is selected directly without a router/governing invocation that requested write-back, do not infer new mutation authority merely from this prompt's existence; report the assessment without writing unless separate authority explicitly establishes a recording mode.

In read-only mode, suppress every review-record mutation: do not submit a formal review, top-level review body/comment, inline review comment, issue/PR fallback comment, or single-maintainer durable fallback record. Report the logical disposition in chat only.

Reach the substantive conclusion from freshly inspected evidence. Do not inherit the prior session's approval/rejection reasoning, do not weaken the governing contract to obtain approval, and distinguish blocking findings from non-blocking observations.

Classify the review target before deriving the review surface. When current authoritative lifecycle state identifies the exact review target as an architecture-closure artefact with `CLOSURE_REVIEW_REQUIRED`, set `REVIEW_TYPE=ARCHITECTURE_CLOSURE` and bind the review to that exact durable closure identity. This is a review of the closure model before candidate projection, not a review of a candidate that already consumes the model. Independently reconstruct the applicable source/obligation universe and closure requirements; the author-side `ARCHITECTURE_CLOSURE_READY` conclusion is navigation evidence only.

For `REVIEW_TYPE=ARCHITECTURE_CLOSURE`, actively attempt to falsify source/obligation completeness, source → primitive totality, producer/consumer ordering and currentness, global identity/provenance constructibility, authority issuer/owner/scope/freshness/cardinality/consumption/reissue, extensional consequence ownership/disjointness, external-effect claim/result/ambiguity/recovery, failure/crash/retry/partial-success totality, terminal provenance, positive normal and recovery reachability, migration/fence/cutover closure where applicable, and whether the model is anchored at the actual production/platform/framework authority boundary. Return exactly one closure-review disposition: `APPROVED_FOR_CANDIDATE_PROJECTION` or `CHANGES REQUIRED`. Approval is bound to the exact closure artefact and means only that separately authorised candidate projection may consume it; it is not candidate, implementation, merge, deployment or execution approval. `CHANGES REQUIRED` keeps candidate projection ineligible and returns to closure revision/reconstruction rather than `/fix`. That disposition permanently rejects the exact reviewed closure snapshot; a corrected closure must be frozen as a new snapshot generation before another genuinely fresh closure review.

Before treating the substantive review as complete, derive a bounded decision-critical review surface for the exact **review target** from the governing contract and acceptance criteria, repository-local instructions, applicable trust, safety, authority and evidence boundaries, and dependency/runtime semantics that can materially affect the decision. For candidate review, derive a bounded decision-critical review surface for the exact candidate and include the material candidate/diff; for `REVIEW_TYPE=ARCHITECTURE_CLOSURE`, derive the surface from the exact durable closure artefact, its governing bindings and authoritative environment without manufacturing a not-yet-projected candidate identity. Prior blocking findings are navigation/context only; they do not substitute for re-examining the complete current surface. Derive domains from this current governing evidence rather than applying a universal checklist or expanding the review into an exhaustive repository-wide audit.

When the exact review target is a candidate and is materially stateful, lifecycle-sensitive, cross-component, concurrency/retry/cache/inference-sensitive, or equivalent, proportionately include the applicable production integration paths, stale and in-flight completion behaviour, partial-success and incomplete-result behaviour, failure/retry/recovery paths, duplicated raw conditions or policy bypasses, new failure handling introduced by remediation, and the evidence required to justify negative inference. These are candidate-derived review domains, not a universal state-machine checklist for every review.

Retain compact reconstructable coverage logically equivalent to `review domain -> PASS | BLOCKER | NOT_APPLICABLE`. A domain may be `NOT_APPLICABLE` only when current evidence establishes that it does not affect this decision. Do not claim the review surface is complete while an applicable decision-critical domain remains unexamined. Coverage evidence may remain internal or implicit in structured reasoning/evidence state; do not emit a verbose checklist by default.

Discovering a material blocker determines that approval is impossible, but it does not end the substantive inspection. Continue through the bounded decision-critical review surface for the exact review target before recording the disposition. For candidate review, continue through the bounded decision-critical review surface for the exact candidate before recording the disposition. For `CHANGES REQUIRED`, report all material blockers discovered across that completed surface. A statement such as `I found no other material blocker`, or any equivalent completion claim, is valid only after the bounded surface has been completed.

After the bounded review surface is complete and material findings are identified, assess their relationships proportionately when current findings, or prior materially related findings used only as navigation/evidence, indicate that they may share an invariant, mechanism, trust boundary, parser/lifecycle behaviour, or implementation abstraction. Do not infer an abstraction failure from the number of findings and do not require a universal defect taxonomy. Determine whether the findings are isolated defects in an otherwise sound abstraction or manifestations of a shared failure. When evidence indicates a shared defect family, challenge whether the current abstraction or boundary remains sound before recommending another local exception. If the abstraction remains sound, a bounded local remediation may remain appropriate only when no stronger post-closure governance boundary is already established. If durable evidence shows the family already underwent invariant closure and the current blocker is independently established as materially same-family within that closure boundary, record enough relationship evidence for later routing to recognise post-closure recurrence; do not recommend ordinary `/fix` as though the prior closure attempt did not exist. If one invariant/boundary correction is objectively the minimum safe correction and is already within the governing contract and remediation authority, that correction may be recommended only when the current lifecycle state permits ordinary remediation. If the needed abstraction change requires materially new product, architecture, security, scope, or authority, expose that planning/decision/authority boundary rather than manufacturing `/fix` authority. Relationship assessment may remain internal or implicit; keep the human-facing review concise unless the relationship itself is decision-critical rationale.

Treat green CI and passing regression examples as evidence for the behaviours and cases currently specified, not as automatic proof that the underlying invariant or abstraction is sound. Do not let passing example tests suppress substantive relationship/invariant review when the candidate evidence indicates a materially related escape family.

When this is a fresh re-review after `/fix` or another authorised remediation, verify the prior remediations against the new exact candidate and also derive and complete the full currently applicable decision-critical review surface again. Closing the previous blocker is necessary evidence but is not equivalent to establishing that the new exact candidate is substantively sound. Do not restrict re-review to the previous findings, and do not carry candidate-A coverage forward as proof that candidate B's surface was completed.

If the authoring/remediation context produced a `REMEDIATION_READINESS_SWEEP` record, treat it only as navigation and evidence about candidate identity, changed surface, tests/validation actually executed, remaining explicitly untested surface, and recorded authority boundaries. Do not inherit its substantive conclusion that the candidate is complete or sound, do not narrow this review to the author's challenge matrix, and do not treat `REMEDIATION_READINESS_SWEEP=COMPLETE`, `REMEDIATION_COMPLETE_PENDING_FRESH_REVIEW`, or an equivalent author-side record as `APPROVED`, `CHANGES_REQUIRED`, formal review state, or satisfaction of fresh-review independence. Independently reconstruct the applicable review surface and adjudicate the exact candidate under this review contract.

For later learning or measurement, classify a review escape narrowly: a material blocker discovered by a later substantive review in a decision-critical domain that was already applicable and materially unchanged when an earlier review treated that domain or review surface as complete. Do not classify a defect as an earlier review escape when the intervening remediation introduced it, the governing requirement became applicable only later, a material candidate change created a new review domain, new external evidence legitimately changed the decision, or the earlier review explicitly recorded the domain as not yet reviewed or out of scope rather than complete.

Fresh independence is a property of this reviewing context and its information boundary, not automatically of the GitHub account used to record the result. In a single-maintainer repository, a genuinely fresh context may use the same maintainer account that authored the PR. Do not treat same-account operation as a loss of independence unless repository-local policy, branch protection, regulation, or explicit task authority requires a distinct reviewer identity.

A delegated isolated context must not be used to simulate compliance with a repository-local requirement for another human, distinct formal reviewer identity, or formal approval state. If such a requirement genuinely applies and the delegated context cannot satisfy it, preserve that stronger rule and fail/hand off rather than representing model-context isolation as the required human separation.

When write-back is active for a GitHub pull request, distinguish the logical Promptbook disposition from the hosting-platform review event. Map an approval/no-blocking-findings result to GitHub `APPROVE` where permitted; map material blockers requiring correction before acceptance to `REQUEST_CHANGES` where permitted; use `COMMENT` for neutral/advisory reviews, questions, non-blocking observations, or a repository/platform fallback that must not be represented as formal approval/change-request state. Do not force an undecidable or non-formal logical result into a false formal GitHub state.

When write-back is active for a non-PR `REVIEW_TYPE=ARCHITECTURE_CLOSURE` artefact anchored in a GitHub issue/comment, do not attempt a formal PR review. Publish exactly one new top-level comment on the owning issue after refreshing the exact closure snapshot identity. The comment must state `REVIEW_TYPE=ARCHITECTURE_CLOSURE`, the exact closure snapshot identity, and exactly one disposition (`APPROVED_FOR_CANDIDATE_PROJECTION` or `CHANGES REQUIRED`). After publication, bind the returned issue-comment locator to an edit-sensitive review-record snapshot identity and to the exact closure snapshot reviewed. The locator alone cannot satisfy `CLOSURE_REVIEW_REQUIRED`, and an in-place edit invalidates the record for later consumption. A chat-only result, an unbound issue comment, or a record for a different closure snapshot cannot satisfy the gate.

Immediately before publishing any durable review record, refresh the exact review-target snapshot identity and reconcile material movement; for a mutable issue/comment target, re-read the current body/version witness rather than comparing only the object locator. For a GitHub pull-request candidate review, immediately before submitting a GitHub review record, refresh the exact pull-request/head identity and bind the review to the candidate actually inspected. If the candidate moved materially enough that the completed review is stale or no longer safely applicable, do not blindly submit it; re-review the changed candidate or fail/hand off according to the governing freshness, evidence, and authority rules.

Inline review comments may accompany the review only when exact changed-line or range context materially improves precision, actionability, or remediation accuracy. Do not create inline comments to satisfy a count, duplicate the top-level rationale, or add noise where the review body is sufficient.

When same-account PR authorship is already established, the repository is operating under the single-maintainer model, and no repository-local policy, branch protection, regulation, or explicit task authority requires a distinct reviewer or formal approval status, do not attempt a formal self-`APPROVE` or self-`REQUEST_CHANGES` that the hosting platform cannot record. When write-back is active, record the exact disposition and concise rationale through a permitted `COMMENT` review, durable PR comment, issue comment, or other repository-local record permitted by policy, clearly distinguish that record from formal platform review state, then return control to the governing workflow. When read-only mode is active, do not create that fallback record. The inability to record such a formal self-review remains a recording limitation rather than a governance stop by itself; when it is known in advance, avoid the pointless failed call rather than using the failure as discovery. If those preconditions are not established, or a stronger rule requires formal or distinct-person approval, preserve that requirement and fail or hand off rather than assuming the single-maintainer fallback. Do not invent another identity, bypass a required approval, or represent the durable record as a formal platform approval.

If expected state changed, determine what changed and whether the review remains safely decidable; do not fail mechanically merely because an identity moved when the governing contract permits reconciliation.

For each material finding that affects the disposition, retain evidence-bearing provenance logically equivalent to: claim, affected code/location, applicable authority/rule, observation, evidence, exact immutable/durable review-target identity, immutable candidate identity when applicable, priority, and confidence. Classify supporting evidence honestly as STATIC when it is source or rule observation only, EXECUTED when an action or test was actually run and observed, and DURABLE when retained repository-hosted evidence was inspected. Do not fabricate executed evidence from static analysis. The human-facing review may remain concise, but its decisive findings, completed review surface, and disposition must be reconstructable from the bound candidate and evidence.

For a material stateful blocker that may participate in repeated-review or post-closure routing, retain enough concise relationship evidence to reconstruct its behavioural/invariant domain and its independently established relationship to prior durable evidence. Distinguish at least: a new defect family; same-family recurrence before invariant closure; regression of an already-established contract; and post-closure same-family recurrence. For a new defect family that is materially adjacent to the immediately preceding remediation, also record whether current evidence establishes an omitted shared-model dimension: a necessary semantic owner, state dimension, identity/currentness relation, transition class, recovery path, equivalence relation or effect boundary that the remediation did not represent and whose inclusion can change correctness beyond the named reproduction. Record this as `ADJACENT_MODEL_OMISSION` only when independently established; adjacency, shared terminology or finding count alone is insufficient. For a possible post-closure recurrence, retain enough evidence to identify the relevant prior invariant-closure attempt and whether the pertinent invariant/surface remained materially within that closure boundary or was materially changed by an intervening candidate. When the lineage includes a prior `APPROVED_FOR_CANDIDATE_PROJECTION` closure review, independently distinguish a local regression inside a still-sound represented model from an equivalent same-family **structural** falsification of the approved closure/model. Record `EQUIVALENT_SAME_FAMILY_STRUCTURAL_FALSIFICATION` only for the latter; that classification requires the later complexity disposition before model expansion. A fresh reviewer must not inherit an author-side conclusion that a finding is same-family, post-closure recurrence, structural falsification or adjacent-model omission; establish the relationship independently from the current review target and durable evidence. This evidence supports later routing only; it must not turn finding count or historical closure lineage into an automatic abstraction diagnosis.

When the candidate claims architecture closure or is derived from an architecture-closure record, independently review **internal model correctness**, **source-universe completeness**, and **source → primitive/model coverage**. Do not inherit the author's claim that the closure artefact contains every applicable decision-critical obligation or primitive. Derive a bounded independent challenge surface from the governing contract, authority boundaries, externally observable consequences, mutable state, identity dependencies, recovery/ambiguity obligations and migration/cutover obligations. First attempt to identify an applicable authoritative obligation or externally observable consequence omitted from the closure record's source/obligation universe. Then attempt to identify an inventoried obligation with no primitive mapping, an undeclared object/state/operation/authority/effect, a state-sensitive authority whose exact state/revision/epoch/freshness binding is absent or unproved, or an admissible effect path whose same-consequence canonical ownership or disjointness is unproved. Challenge whether authoritative movement invalidates, consumes or reissues state-sensitive authority, and whether later return to a compatible named state could revive stale authority. Primitive → source traceability is not evidence of source → primitive completeness.

Also independently challenge the **publication-gate lineage** for a strong closure claim. Establish whether the candidate is materially security-/authority-/identity-/recovery-/effect-/migration-sensitive, whether it is actually making a strong completeness claim, whether a current independent closure artefact existed before the candidate was treated as closure-ready, whether the candidate was derived from that artefact rather than defining its own completeness universe, and whether material governing-contract or architecture-scope movement made the artefact stale. A high-risk strong-completeness candidate that escaped the proactive gate, or that relies on candidate-derived self-closure, is not approval-eligible even if its prose is internally consistent. Conversely, do not demand architecture-closure evidence for ordinary exploratory, explicitly incomplete or bounded local design solely because architecture/security terminology appears.

For each material architecture-closure finding, first distinguish `MODELLED_BUT_WRONG` from an omitted/structural failure. `MODELLED_BUT_WRONG` is eligible for the strong-closure generation's bounded semantic-correction route only when the applicable obligation/primitive is already represented by the canonical model, governing scope and authority are unchanged, and every material blocker is wholly internal to that represented universe.

Use `NEW_OR_OMITTED_OBLIGATION` / `UNMODELLED_DECISION_CRITICAL_PRIMITIVE` only when the obligation, primitive or relation was already authoritative/applicable to the reviewed closure scope, should have been represented in the canonical closure universe, was absent rather than merely incorrectly instantiated, and materially affects safety, authority, constructibility, reachability, recovery, identity, effect correctness or terminal correctness. That finding is immediately blocking; it does not need a separate scope-amendment decision before it can invalidate the current generation.

Use `STRUCTURAL_FALSIFICATION` when the finding proves the current closure method/model structure is inadequate rather than merely locally wrong. Use `SCOPE_OR_AUTHORITY_MOVEMENT` when correction would change the governing source/obligation boundary, assurance claim, architecture scope or authority basis. Treat a truly semantic-model-invariant packaging/reproducibility defect as `PACKAGE_ONLY_DEFECT`.

For `REVIEW_TYPE=ARCHITECTURE_CLOSURE`, fresh review owns the routing classification of the completed material blocker set. If findings overlap categories, correction eligibility is ambiguous, or any material finding is new/omitted, structural, scope-moving or authority-moving, fail closed to `GOVERNING_DISPOSITION_REQUIRED`. Author-side evidence may support facts but cannot downgrade that route. A modelled local defect, newly applicable requirement after the frozen governing boundary, unrelated family, duplicate adjudication or represented design disagreement does not by itself establish structural falsification.

Return exactly one clear disposition appropriate to the gate. For `REVIEW_TYPE=ARCHITECTURE_CLOSURE`, use `APPROVED_FOR_CANDIDATE_PROJECTION` or `CHANGES REQUIRED`; for ordinary candidate/design/evidence review use the existing `APPROVED` / `CHANGES REQUIRED` (or other repository-appropriate) semantics. Follow the disposition with concise decisive rationale. For a negative disposition, identify only material blockers that must be resolved, including every material blocker discovered across the completed bounded review surface; do not dump the internal coverage model unless it is materially needed to explain the decision.

That single disposition is the review record. If this review was explicitly requested as the final deliverable, stop after recording or reporting it according to the selected recording mode. When the broader governed objective remains active and the next invocation is safely determined from durable authoritative state, append one minimal `Next:` invocation after the disposition. That line is navigation metadata only: it does not execute continuation in this context and does not grant mutation, merge, implementation, execution, or other authority. If the disposition is `APPROVED_FOR_CANDIDATE_PROJECTION`, prefer `/go` targeting the governing objective so current projection authority can be resolved separately; do not imply that a candidate already exists or is approved. If the disposition is APPROVED, prefer `/go` targeting the governing objective rather than merely echoing an intermediate reviewed artefact when that target reconstructs the complete lifecycle. If an architecture-closure review returns `CHANGES REQUIRED`, do **not** suggest `/fix`. Record the review-owned route classification: one eligible `MODELLED_DEFECT` may return through the generation's unused semantic-correction allowance; one eligible `PACKAGE_ONLY_DEFECT` may return through the unused package-only repair allowance; `NEW_OR_OMITTED_OBLIGATION`, `STRUCTURAL_FALSIFICATION`, `SCOPE_OR_AUTHORITY_MOVEMENT`, ambiguous classification or exhausted allowance routes to `GOVERNING_DISPOSITION_REQUIRED`. Do not automatically create another closure generation. If the disposition is CHANGES REQUIRED, suggest `/fix` only when bounded remediation is already the safely authorised next path; otherwise expose the actual decision, blocker, or external boundary instead of manufacturing remediation authority. For `REVIEW_TYPE=ARCHITECTURE_CLOSURE`, bounded remediation is not the next path, so the preceding closure-specific rule wins.

If this is a delegated fresh review, return the disposition/evidence record with the exact review-target identity actually inspected, the exact candidate identity when applicable, and enough bounded isolation/projection provenance for the originating workflow to verify that the review came from an eligible fresh context. For candidate review, retain the exact candidate identity actually inspected as the candidate-specific binding. Do not return private reasoning or hidden chain-of-thought. The originating workflow must refresh the exact review target and review state before relying on the result, plus candidate identity when applicable; stale delegated review evidence does not transfer across material target movement.

If a governing workflow or router invoked this review as an intermediate gate, return control to that workflow after recording or reporting the disposition according to the selected mode; do not treat review completion itself as a terminal state.

A review result never creates mutation authority beyond the review-record write already intrinsic to an ordinary router `/review`. A recorded `APPROVE` is review evidence/state, not merge authority. A recorded `REQUEST_CHANGES` identifies blockers, not remediation authority. A recorded `COMMENT` is not acceptance unless repository-local policy explicitly gives it that meaning. If CHANGES REQUIRED identifies bounded defects whose minimum-safe remediations are objectively determined and already authorised by the governing task, the governing workflow may enter the bounded remediation cycle without another routine approval, run required validation, and complete the proportional author-side remediation-readiness sweep before freezing the review-ready candidate. The completed blocker set determines the remediation plan and starting scope, but it is not an exhaustive search universe for the readiness sweep. If that sweep discovers another objectively bounded sibling defect, it may be corrected in the same cycle only when the correction remains attributable to the resolved remediation scope and independently passes the `/fix` action gateway as `ALLOW`; otherwise the new evidence returns to the existing authority/design/escalation rules rather than widening remediation. Minimum-safe remediation is not synonymous with the most local textual patch: where the completed review establishes a shared invariant/boundary failure and one invariant/boundary correction is objectively determined and already authorised, that correction may itself be the bounded minimum-safe remediation. Otherwise, the remediation must not proactively redesign adjacent components merely because the completed review exposed more than one blocker. Once this context authors or materially shapes the changed candidate or readiness evidence, it must not claim a fresh independent review of that changed candidate; route the exact frozen candidate to a genuinely fresh review context before any gate that requires independence. In a single-maintainer repository, that new fresh context may still use the same GitHub maintainer identity.

If the disposition is APPROVED, the governing workflow may continue any already-authorised merge, verification, and close-out work. Do not stop merely because the review gate completed or because the platform cannot record a formal self-approval when the overall governed task still has authorised, safely decidable work remaining. If repository rules genuinely require a distinct reviewer identity or formal approval status, preserve that requirement and fail or hand off according to the governing workflow rather than bypassing it.

## Inputs

- `<REVIEW_TARGET>` — the exact PR, commit, design, evidence record, or other candidate to assess.
- `<GOVERNING_CONTRACT>` — the issue, specification, acceptance criteria, design, policy, or explicit review contract.

## What it does

Creates an information boundary between authoring and adjudication and forces the reviewer to inspect the real evidence rather than merely validating a handover summary. Before substantive adjudication it resolves the ephemeral [Resolved agent run context](resolved-agent-run-context.md), binding authority, capability boundaries, exact review-target identity, candidate identity when applicable, instruction provenance, and required evidence to the review operation. When invoked through fresh-review context resolution, it additionally requires affirmative isolation from author-side substantive adjudication, minimal durable target transfer, independent authority/review-target reconstruction with candidate identity when applicable, a child capability set bounded by the ordinary `/review` ceiling, and exact-review-target result binding. It also requires a bounded decision-critical review surface to be derived from current governing evidence and completed before disposition, so the first blocker ends approval eligibility without ending substantive inspection and a negative review reports the material blocker set found across that completed surface. Coverage remains reconstructable without requiring verbose checklist output. After that surface is complete, materially related findings are synthesised proportionately so a shared invariant, mechanism, trust boundary, or abstraction is challenged before another local exception is recommended, without turning recurrence into an automatic redesign rule. Fresh re-review after remediation verifies the known fixes and re-runs the complete currently applicable surface against the new exact candidate, while review-escape semantics distinguish missed unchanged blockers from legitimately later defects or requirements. When selected by ordinary router `/review` for a GitHub pull request, it records the requested review by default while limiting authority to that review record; an explicit read-only qualifier suppresses all write-back. Direct standalone use remains non-mutating unless a governing invocation separately establishes write-back authority. When composed inside a governing workflow, it records or reports the independent disposition without turning review completion into an unnecessary conversational stop. When review itself is the requested final deliverable, it also provides minimal navigation to the next governed invocation when the broader objective remains active and that invocation is safely determined, without performing that continuation. It also separates reasoning independence from hosting-platform reviewer identity so single-maintainer projects can retain fresh-context review without inventing extra accounts or false approval gates.

## Boundaries / limitations

Freshness is a property of prior information, not a prompt incantation or a different account name. A context that substantially authored the candidate or already saw the expected answer cannot become independent merely by being told to forget it, even if it uses another account, process, tool or model label. Conversely, a genuinely fresh context does not cease to be independent merely because a single-maintainer project must use the same GitHub identity. Delegated freshness must be established from the receiving context's information boundary; if that isolation is unavailable or unprovable, the delegated context is ineligible and the governing workflow retains the manual fresh-context fallback. Authoritative rules may be shared; author-side substantive adjudication and private reasoning may not be supplied as review evidence. The bounded review-completion invariant is scoped to the decision being made; it is not a universal checklist or a requirement to audit every imaginable concern in the repository. Relationship assessment is evidence-driven rather than count-driven and does not require a universal defect taxonomy or automatic architectural escalation. Repository-local requirements for distinct reviewers, formal approvals, or no-write operation still take precedence. The review result does not grant mutation authority beyond the requested review record; any remediation, merge, release, deployment, settings, credential, production, or other continuation must already be authorised by the governing task or workflow. Suggested next invocations are navigation only and must not substitute for a decision capsule, a genuine blocker, or a complete executable external-action handoff.
